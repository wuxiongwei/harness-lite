## 1. 业务背景与动机

### 1.1 用户场景

H-L Lite 档（v1.0.21 已完成）解决了**单人 / 小团队效率**问题。
但产品宪法 §03-target-users 画像 D（6-15 人中等团队）核心痛点是**多人协同**。

用户原话："Standard 人就多了，可能无法自己人为的划分功能如何分工，分支如何管理，甚至这时候有人会专门负责测试，对于产品全量的回归等等进行专门的考虑，产品可能会多一个架构的设计等等的，**也就是人多了说明产品复杂了，那我们就要设计出多人可以协同的功能，这才是 Standard**。"

### 1.2 关键洞察（用户拍板）

| 旧理解 | 新理解 |
|------|------|
| Standard = 人数多 | **Standard = 复杂度高（人多是结果）** |
| Standard = Lite + 角色 | Standard = **多人协同机制** |
| 工业化分工（PM/RD/QA 隔离） | **协同视角**（每个角色互看、互补） |

**v1.0.21 v1（角色分工已废）的教训**：分工 ≠ 协同。多人在 AI 时代不需要被切开，而需要更好的协同基础设施。

### 1.3 痛点

具体场景举例：
- **并行不冲突**：A 在改 `src/services/user.py`，B 不知道 A 在改，也来改 → 冲突
- **责任不重复**：全量回归该 A 跑还是 B 跑？没人负责 → 漏检
- **角色协同缺失**：PM 写的需求 RD 看了说"AC 不清晰"，QA 看了说"边界缺失" → 返工

### 1.4 价值主张

**让多人在同一个项目上并行工作而不彼此踩脚 + AI 帮助跨角色互补**。

## 2. 功能需求

### 2.1 MVP 范围（用户拍板：A1+A2+A3+B1）

| # | 功能点 | 说明 | 优先级 |
|---|-------|------|--------|
| **A 类：并行不冲突** | | | |
| A1 | 分支策略约定 | `.claude/branch-strategy.md` 团队约定 + AI 在 commit/push 时**软提醒**（不强制） | P0 |
| A2 | 任务认领板 | `.claude/assignments/<人>.md` 个人维度 + AI 在 task 冲突时提醒 | P0 |
| A3 | 代码冲突预警 | `/harness-impact` 增加"其他人正在改这个文件吗"检查 | P0 |
| **B 类：角色协同** | | | |
| B1 | 协同视角 | PM 调 `/harness-req` 时，AI 在产物末尾追加"RD 视角提醒"+"QA 视角提醒" | P0 |

### 2.2 不做的范围（v1.0.24+）

- ❌ **C 类（知识协同）**：共享 wiki / 架构 ADR / 设计评审协作 → 单独大版本
- ❌ **强制 git hook 分支校验**：用户拍板"最轻"——只 .claude 文件约定 + AI 软提醒，不动 hook
- ❌ **任务维度的认领文件**：用户拍板用"个人维度"
- ❌ **工业化分工**（v1.0.21 v1 已废）：协同 ≠ 分工
- ❌ **多人实时同步**：本地 markdown 文件，靠 git 同步即可
- ❌ **任务依赖图 / 时间线**：只 claim，不做项目管理

### 2.3 详细方案

#### A1 · 分支策略约定

**`.claude/branch-strategy.md`（团队共享文件，入仓库）**：

```markdown
# 分支策略（团队约定）

## 命名规范
- feat/<ticket-id>-<short-name>     # 新功能
- fix/<ticket-id>-<short-name>      # bug 修复
- refactor/<short-name>             # 重构
- docs/<short-name>                 # 文档

## 主分支保护
- main：禁止直推
- develop：仅团队 lead 可推

## 合并规则
- 必须经过 review
- 必须通过 pre-commit hook
- 必须 squash merge

## 当前分支建议
（团队按需自定义）
```

**AI 在 commit / push 时的行为**：
1. Read `.claude/branch-strategy.md`
2. 检查当前分支名是否符合命名规范
3. 不符合 → **软提醒**（不阻塞）："当前分支 `xxx` 不符合命名规范，建议改名"
4. 符合 → 静默通过

#### A2 · 任务认领板

**`.claude/assignments/<姓名>.md`**：

```markdown
# 任务认领（zoe）

## 进行中（claimed）
- v1.0.23-standard-collaboration · 阶段 3 编码 · 自 2026-06-18

## 待办（pending）
- v1.0.24-knowledge-share · 待 v1.0.23 完成

## 已完成（done）
- v1.0.21-lite-automation · 完成于 2026-06-18
```

**AI 在 task 冲突时的行为**：
1. 用户调 `/harness-req` 创建新版本目录前
2. Read 所有 `.claude/assignments/*.md`
3. 检查目标版本目录是否已被 claim
4. 已 claim → **软提醒**："`v1.0.23` 由 alice claim，确认你也要参与？"
5. 未 claim → 在当前用户的 assignments 文件追加 claim 记录

#### A3 · 代码冲突预警

**扩展 `/harness-impact`**：

原行为：分析 git diff → 列出依赖。

新增：
1. Read `.claude/assignments/*.md` 所有人
2. 检查改动文件路径是否被其他人 claim
3. 如有冲突 → 报告中标注："⚠️ `src/services/user.py` 也被 alice claim 在 v1.0.24 中改"
4. 用户决定如何处理（沟通 / 拆分 / 顺序化）

#### B1 · 角色协同视角

**扩展 `/harness-req`（默认 PM 视角）**：

主产物（01-需求.md）格式不变。**末尾新增**协同视角段：

```markdown
---

## 🔍 角色协同视角

### 🛠️ RD 视角提醒
- 实现可行性：搜索功能涉及全文索引 vs LIKE 查询的方案分叉
- 估时分歧：10W vs 100W 数据量级架构差异
- 风险：是否需要引入 ES？

### 🧪 QA 视角提醒
- 边界场景：空结果 / 超长输入 / 特殊字符 / 中文分词
- 测试矩阵：单查 / 多查 / 高并发
- 性能：响应 < 500ms 验证方法
```

**这个不是 v1.0.21 废掉的"多视角增强"**：
- v1.0.21 是"一个 skill 给多视角" → 用户视角同时看
- v1.0.23 B1 是"协同视角段" → 让团队不同角色（PM 写、RD 看、QA 看）能看到对方关注点

类似扩展也可以在 `/harness-design`（PM/QA 视角看设计）和 `/harness-test-ci`（PM/RD 视角看测试报告）做。**v1.0.23 MVP 只在 `/harness-req` 落地一处**，验证有效再扩展。

### 2.4 非功能需求

| 维度 | 要求 |
|-----|------|
| 向下兼容 | v1.0.22 装的项目升级后，新文件不存在 = 行为不变（同 v1.0.21 升级路径） |

| 不入仓库 | 与 Lite 不同：assignments **入仓库**（协同需要） |
| 软约束优先 | 全部"软提醒不阻塞"——不强制 git hook，避免破坏现有团队 workflow |

### 2.5 边界与约束

**做什么**：
- ✅ 4 个 MVP 功能（A1/A2/A3/B1）
- ✅ 文件层（branch-strategy + assignments）入仓库
- ✅ 软提醒不阻塞
- ✅ 向下兼容

**不做什么**：
- ❌ C 类知识协同（v1.0.24+）
- ❌ 强制 git hook 分支校验
- ❌ 任务依赖图 / 时间线 / 项目管理
- ❌ 多人实时同步机制
- ❌ 任务维度文件结构
- ❌ 工业化分工 / 角色 skill 隔离
