# 三层防护架构（规则 + 权限 + 执行）

> 来源：Harness-Lite v1.0.12 删除 block-push.sh 时总结

---

## 架构概览

Harness-Lite 对"AI 不安全行为"的防护采用三层架构：

```
┌─────────────────────────────────────────┐
│ Layer 1: 规则层（principles.md）        │  ← 软约束，AI 自觉遵守
│ "AI 不主动 commit/push"                 │
└─────────────────────────────────────────┘
                ↓ 若 AI 违反
┌─────────────────────────────────────────┐
│ Layer 2: 权限层（settings.json deny）   │  ← 硬拦截，Claude Code 执行前拦
│ deny: ["Bash(git push --force *)"]     │
└─────────────────────────────────────────┘
                ↓ 若危险操作漏过
┌─────────────────────────────────────────┐
│ Layer 3: 执行层（PreToolUse hook）      │  ← 动态检查，可加业务逻辑
│ pre-commit-test.sh                      │
└─────────────────────────────────────────┘
```

## 设计原则

### 1. 每层有清晰边界

| 层 | 职责 | 失效后果 |
|----|------|---------|
| 规则层 | 告诉 AI"应该/不应该"做什么 | AI 偶发违反 → Layer 2 拦 |
| 权限层 | 拦截已知危险操作模式 | 新危险模式漏过 → Layer 3 补 |
| 执行层 | 业务逻辑自定义检查（如全量测试） | 失效 → 用户手动介入 |

### 2. 不过度叠加

**反例**：v1.0.5-v1.0.11 曾有 `block-push.sh`（Layer 3 拦所有 push）：
- Layer 1 已规定"AI 不主动 push"
- Layer 2 已拦 `git push --force *`
- Layer 3 再拦**所有** push → **冗余 + 扰民**

**删除理由**：
- 三层防护中第三层无法区分"AI 主动 push" vs "用户授意 AI 帮 push"
- 后者是合理场景，被一刀切拦截

### 3. 加新防护的 checklist

每加一层防护必须问 3 个问题（v1.0.12 沉淀）：
1. 已有几层覆盖同一场景？
2. 这一层独有覆盖什么前 N 层不能覆盖的？
3. 这一层会误拦什么合理场景？

任一答得不好 → 不加。

## 实例：commit 防护

| 场景 | Layer 1 | Layer 2 | Layer 3 |
|------|---------|---------|---------|
| AI 主动 commit 普通改动 | 规定"不主动" ✅ | — | — |
| AI commit 但没跑测试 | — | — | pre-commit-test.sh 拦 ✅ |
| 用户授意 AI commit | Layer 1 允许 ✅ | — | Layer 3 检测通过 ✅ |

→ 三层**各司其职**，不冗余。

## 与本产品其他机制的关系

| 机制 | 对应层 |
|-----|-------|
| `principles.md` 12 条行为准则 | Layer 1 |
| `settings.json` permissions.deny | Layer 2 |
| `pre-commit-test.sh` / `distill-prompt.sh` | Layer 3 |
| `validate.sh`（5 维自检） | 预防层（安装时检测配置错误） |

## 教训

- 不是"层越多越安全"——每层都有**维护成本** + **误拦风险**
- Layer 3（hook）最灵活但也最容易过度设计
- 删除 Layer 的勇气 > 添加 Layer 的惯性
