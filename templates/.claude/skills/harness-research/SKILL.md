# /harness-research · 多 Agent 并行调研

> **需求前置 · 信息收集环节**：一个主题拆 N 个维度，并行启动 N 个 Agent
> 结构化产出，软验证质量，不跑评分公式

---

## 定位

在动手做需求/设计前，先把背景信息搜清楚。把一个调研主题拆成多个独立维度，
每个维度派一个 Agent 并行搜索，最后汇总成结构化报告。

- **并行**：N 个维度 = N 个 Agent 同时跑，不串行等待
- **结构化**：每个维度产一个 markdown 文件，含 `meta` 块（来源/类型/要点）
- **防假完成**：Agent 会"自报完成"但实际没写文件，必须验证
- **软验证**：Claude 读 meta 块定性判断质量，不算量化评分（保持 harness-lite 纯净）

**何时用**：竞品分析 / 技术选型 / 人物研究 / 市场背景调查 / 需求前的信息收集。
**何时不用**：信息已经清楚、只需要一两次搜索就能回答的问题（直接用 WebSearch 即可）。

## Phase 1：确认调研配置

收到主题后确认三件事：

```
1. 调研主题：调研什么？
2. 调研类型：用预设模板还是自定义维度？
3. 输出目录：默认 docs/versions/active/v{X.Y.Z}-{slug}/research/
```

### 预设模板速查

| 模板 | 维度数 | 适用场景 |
|------|--------|----------|
| `person`  | 6 | 人物思维蒸馏、专家研究、创始人背景 |
| `company` | 5 | 竞品分析、投资尽调、合作方调查 |
| `tech`    | 4 | 技术选型、框架评估、学习路径 |

> 用户说"调研 XX"没给更多信息 → 根据主题自动选模板，直接推进，不反复追问。
> 人物类可选传 `role_hints`（角色补充搜索点），见 person 模板说明。

## Phase 3：并行启动 Agent

为每个维度生成一个 Agent 任务，**全部在同一条消息中启动**（并行执行）：

```
对每个维度 dim：
  Task(
    subagent_type: "general-purpose",   # 或项目自定义的 researcher agent
    description: "调研维度：{dim.name}",
    prompt: """
      你是调研员。针对主题「{topic}」的「{dim.name}」维度做深度搜索。

      搜索目标：
      {dim.search_targets 逐条列出}

      提取焦点：{dim.extract_focus}

      信息源优先级：{source_strategy.priority}
      避免使用：{source_strategy.blacklist}
      尽量提高一手资料占比（目标 ≥ {first_hand_ratio_target}）

      输出文件：{output_dir}/{dim.output_file}

      格式要求：每个发现写成一个 meta 块——
      ```meta
      source: <URL>
      source_type: 一手 | 二手
      date: <发布日期，未知写 unknown>
      point: <这条信息的核心要点，1-2 句>
      ```
      正文用 markdown 组织，meta 块嵌在对应内容旁。

      硬性要求：
      - 至少 10 个 meta 块
      - 至少 5 个不同域名来源
      - 诚实标注信息缺口（搜不到的写"信息缺口：XXX"）
      - 不同来源矛盾时，单列"矛盾与不一致"section
    """
  )
```

**铁律**：
- 所有 Agent 必须在**同一条消息**里启动（这才是并行；分多条消息是串行）
- 每个 Agent 独立工作，互不读对方产出
- 等全部完成后才进入 Phase 4

## Phase 4：文件存在性验证（必须执行）

> **LLM 子 Agent 会"自报完成"但实际没写文件或写得过少。** 这是 ccflow 踩过的坑，必须验证。

```bash
# 对每个维度的输出文件检查
for 每个 dim:
  字节数 = wc -c {output_dir}/{dim.output_file}
  meta块数 = grep -c '^```meta$' {output_dir}/{dim.output_file}
  if 文件不存在 or 字节数 < 1000 or meta块数 < 10:
    标记该维度需重跑
```

发现缺失/过小：
1. 明确告诉用户哪些维度未达标
2. 重新发起这些维度的 Agent，**prompt 末尾追加硬约束**：
   ```
   完成后必须报告（避免假完成）：
   1. Bash 执行 wc -c <输出文件> 报告字节数（必须 > 5000）
   2. grep -c '^```meta$' <输出文件> 报告 meta 块数（必须 ≥ 10）
   ```
3. 重跑达标后才进入 Phase 5

## Phase 5：Feynman 深度验证（推荐执行）

> 文件存在 ≠ 内容扎实。用 Feynman 视角做第二层质量验证，专治"形式正确但实质空洞"。
> （以下验证标准内嵌，不依赖外部 skill 文件。）

对每个维度的输出，自检 5 个问题：

```
1. 【真实性】信息是否可验证？有没有"听起来对但无法证实"的内容？
   → 抽查 2-3 个 meta 块的 source URL 是否真实可达、是否支撑 point

2. 【理解 vs 命名】是真正理解了底层逻辑，还是只在堆砌术语？
   → 检查是否能用大白话复述，而非只列专有名词

3. 【货物崇拜检测】有没有"格式正确但实质空洞"的条目？
   → 检查 point 是否言之有物，还是套话填充

4. 【矛盾识别】不同来源的信息有没有未标注的矛盾？
   → 检查相互冲突的数据/说法是否被诚实标出

5. 【信息缺口诚实性】是诚实标注"不知道"，还是用模糊表述掩盖？
   → 检查是否有"信息缺口"section，还是假装什么都查到了
```

**验证失败处理**：
- 发现货物崇拜 / 命名替代理解 → 标记该维度补充调研
- 发现未标注矛盾 → 要求 Agent 补"矛盾与不一致"section
- 发现缺口掩盖 → 要求 Agent 补"信息缺口"section

验证通过后进入 Phase 6。

## Phase 6：软验证汇总（不跑评分公式）

> ccflow 用 722 行 Python 算量化评分（死链率/一手占比/多样性）。
> harness-lite 保持纯净：**Claude 读各维度 meta 块，定性判断质量**。

读取所有维度文件，定性评估并生成 `summary.md`（< 500 字）：

```markdown
# 调研摘要：{topic}

## 整体质量（定性）
- 来源充分度：各维度 meta 块数量是否够（目标每维 ≥ 10）
- 一手资料：是否有足够 source_type=一手 的条目
- 维度强弱：哪些维度信息扎实，哪些薄弱

## 关键发现
- （3-5 条跨维度的核心结论）

## 强项维度
- （信息扎实、来源可靠的维度）

## 薄弱维度 / 信息缺口
- （搜不全、来源少、或有未解矛盾的维度）

## 建议
- （是否需要补充调研薄弱维度）
```

> ⚠️ **不输出量化评分、不算死链率公式**。这是刻意的设计取舍——
> 对小团队场景，定性判断够用且零维护成本。

## 错误处理

### 维度 Agent 反复自报完成但文件缺失
```
不要无限重跑。重跑 2 次仍失败 → 告诉用户该维度搜索困难，
可能是主题冷门或关键词不对，建议人工调整搜索方向。
```

### 模板不匹配主题
```
预设 person/company/tech 都不贴合 → 让用户自定义维度
（提供维度名 + 搜索目标 + 提取焦点 + 输出文件名），
按相同流程执行。
```

### 搜索结果普遍质量低
```
Phase 5 发现多数维度货物崇拜 → 停止汇总，
告诉用户原始信息源质量不足，summary 会不可靠。
```

## 使用示例

```
用户：调研一下 Rust 这门语言适不适合我们做 CLI 工具

skill 行动：
  1. 识别为技术调研 → 选 tech 模板（4 维）
  2. 确认输出目录
  3. 同一条消息并行启动 4 个 Agent（原理/场景/生态/演进）
  4. 全部完成后 wc -c + grep 验证文件存在且达标
  5. Feynman 5 问自检（真实性/理解/货物崇拜/矛盾/缺口）
  6. 读 meta 块定性汇总 → summary.md
  7. 报告：哪些维度强、哪些薄弱、是否建议补充
```
