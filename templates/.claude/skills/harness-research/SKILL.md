# /harness-research · 多 Agent 并行调研

> **需求前置 · 信息收集环节**：动态分析主题，推荐维度，并行搜索，结构化产出
> v1.0.35 重构：从固定模板改为动态维度推荐，适配各行各业调研需求

---

## 定位

在动手做需求/设计前，先把背景信息搜清楚。

**核心变化（v1.0.35）**：
- ❌ 不再预设固定模板（person/company/tech）
- ✅ 动态分析用户调研主题 → 推荐合适的维度
- ✅ 内置常见调研类型的参考维度作为起点
- ✅ 用户可确认、增加、删除、调整维度

**v1.0.34+ 新项目启动默认入口**：
- 新项目启动时（无项目上下文）**默认进入调研**
- 用户可显式跳过（说"跳过调研，直接定义需求"），但**不建议跳过**
- 调研目的：在动手定义产品前，先搞清楚市场/竞品/用户需求
- 避免方向错了 → 后面全是白做

**跳过调研的合理场景（仅限，且不建议）**：
- 用户已有充分的市场认知（做过同类产品，清楚竞品格局）
- 内部工具项目（不需要市场分析）
- 用户**非常明确**说出了要做的功能12345，**坚持**跳过调研

**何时用**：
- 新项目启动（默认进入，除非用户显式跳过）
- 技术选型 / 市场调研 / 竞品分析 / 可行性评估 / 行业背景 / 用户需求收集
**何时不用**：信息已经清楚、只需要一两次搜索就能回答的问题（直接用 WebSearch 即可）。

## Phase 1：理解调研主题

收到用户调研请求后，先分析主题：

### 1.1 分析主题关键词

提取用户输入的关键词，判断：
- **调研对象**：技术/市场/公司/产品/行业/用户/项目...
- **调研目的**：选型/评估/了解/对比/决策...
- **行业领域**：如有明确行业标识（如"宠物食品""在线教育"），记录

### 1.2 判断调研类型倾向

根据关键词映射到常见调研类型：

| 关键词示例 | 调研类型倾向 |
|-----------|-------------|
| "XX 技术是否合适""XX vs YY""技术选型" | 技术选型 |
| "XX 市场""市场调研""XX 行业规模" | 市场调研 |
| "可行性""能不能做""值得做吗" | 项目可行性 |
| "竞品""XX 公司""对手分析" | 竞品分析 |
| "行业趋势""政策法规""行业标准" | 行业调研 |
| "用户需求""用户痛点""目标用户" | 用户需求 |
| 无法归类 | 通用信息收集 |

### 1.3 输出主题分析结果

```
调研主题分析：
- 主题：{用户原始输入}
- 调研对象：{技术/市场/公司/...}
- 调研类型倾向：{技术选型/市场调研/...}
- 行业领域：{如有明确标识}
- 调研目的：{选型/评估/了解/决策}
```

### 2.2 推荐机制

根据 Phase 1 的主题分析结果：
1. 匹配调研类型 → 选择对应参考维度
2. 根据具体主题调整维度（如行业特殊要求）
3. 推荐 4-8 个维度（建议上限 ≤ 8）
4. 输出推荐维度列表，格式：

```
推荐调研维度（共 N 个）：

| # | 维度名称 | 搜索目标 | 提取焦点 | 输出文件 |
|---|---------|---------|---------|---------|
| 01 | {维度1} | {搜索目标} | {提取焦点} | `01-{slug}.md` |
| 02 | {维度2} | ... | ... | ... |
```

### 2.3 用户确认

推荐维度后，**必须让用户确认**：

```
请确认调研维度：
- [1] 确认以上维度，开始调研
- [2] 增加维度：告诉我要增加什么
- [3] 删除维度：告诉我编号
- [4] 调整维度：告诉我编号和修改内容
```

用户确认后才进入 Phase 3。

### 2.4 自定义维度

用户可选择完全自定义维度：
- 提供维度名称 + 搜索目标 + 提取焦点
- AI 补充输出文件名
- 按相同流程执行

## Phase 3：并行启动 Agent

为每个确认的维度生成一个 Agent 任务，**全部在同一条消息中启动**（并行执行）：

```
对每个维度 dim：
  Task(
    subagent_type: "general-purpose",
    description: "调研维度：{dim.name}",
    prompt: """
      你是调研员。针对主题「{topic}」的「{dim.name}」维度做深度搜索。

      搜索目标：
      {dim.search_targets 逐条列出}

      提取焦点：{dim.extract_focus}

      信息源优先级：
      - 优先：官方文档/权威报告/一手数据 > 媒体报道/分析文章
      - 避免：营销软文、未验证内容、过时信息（>2年）
      - 一手资料占比目标：≥ 50%

      输出文件：{output_dir}/{dim.output_file}

      格式要求：每个发现写成一个 meta 块——
      ```meta
      source: <URL>
      source_type: 一手 | 二手
      date: <发布日期，未知写 unknown>
      point: <这条信息的核心要点，1-2 句>
      ```
      正文用 markdown 组织，meta 块嵌在对应内容旁。

      硬性要求：
      - 至少 10 个 meta 块
      - 至少 5 个不同域名来源
      - 诚实标注信息缺口（搜不到的写"信息缺口：XXX"）
      - 不同来源矛盾时，单列"矛盾与不一致"section
    """
  )
```

**铁律**：
- 所有 Agent 必须在**同一条消息**里启动（这才是并行；分多条消息是串行）
- 每个 Agent 独立工作，互不读对方产出
- 等全部完成后才进入 Phase 4

## Phase 4：文件存在性验证（必须执行）

> **LLM 子 Agent 会"自报完成"但实际没写文件或写得过少。** 必须验证。

```bash
# 对每个维度的输出文件检查
for 每个 dim:
  字节数 = wc -c {output_dir}/{dim.output_file}
  meta块数 = grep -c '^```meta$' {output_dir}/{dim.output_file}
  if 文件不存在 or 字节数 < 1000 or meta块数 < 10:
    标记该维度需重跑
```

发现缺失/过小：
1. 明确告诉用户哪些维度未达标
2. 重新发起这些维度的 Agent，**prompt 末尾追加硬约束**：
   ```
   完成后必须报告（避免假完成）：
   1. Bash 执行 wc -c <输出文件> 报告字节数（必须 > 5000）
   2. grep -c '^```meta$' <输出文件> 报告 meta 块数（必须 ≥ 10）
   ```
3. 重跑达标后才进入 Phase 5

---

## Phase 5：Feynman 深度验证（推荐执行）

> 文件存在 ≠ 内容扎实。用 Feynman 视角做第二层质量验证，专治"形式正确但实质空洞"。

对每个维度的输出，自检 5 个问题：

```
1. 【真实性】信息是否可验证？有没有"听起来对但无法证实"的内容？
   → 抽查 2-3 个 meta 块的 source URL 是否真实可达、是否支撑 point

2. 【理解 vs 命名】是真正理解了底层逻辑，还是只在堆砌术语？
   → 检查是否能用大白话复述，而非只列专有名词

3. 【货物崇拜检测】有没有"格式正确但实质空洞"的条目？
   → 检查 point 是否言之有物，还是套话填充

4. 【矛盾识别】不同来源的信息有没有未标注的矛盾？
   → 检查相互冲突的数据/说法是否被诚实标出

5. 【信息缺口诚实性】是诚实标注"不知道"，还是用模糊表述掩盖？
   → 检查是否有"信息缺口"section，还是假装什么都查到了
```

**验证失败处理**：
- 发现货物崇拜 / 命名替代理解 → 标记该维度补充调研
- 发现未标注矛盾 → 要求 Agent 补"矛盾与不一致"section
- 发现缺口掩盖 → 要求 Agent 补"信息缺口"section

验证通过后进入 Phase 6。

## Phase 6：软验证汇总

读取所有维度文件，定性评估并生成 `summary.md`（< 500 字）：

```markdown
# 调研摘要：{topic}

## 整体质量（定性）
- 来源充分度：各维度 meta 块数量是否够（目标每维 ≥ 10）
- 一手资料：是否有足够 source_type=一手 的条目
- 维度强弱：哪些维度信息扎实，哪些薄弱

## 关键发现
- （3-5 条跨维度的核心结论）

## 强项维度
- （信息扎实、来源可靠的维度）

## 薄弱维度 / 信息缺口
- （搜不全、来源少、或有未解矛盾的维度）

## 建议
- （是否需要补充调研薄弱维度）
```

## 错误处理

### 维度 Agent 反复自报完成但文件缺失
```
不要无限重跑。重跑 2 次仍失败 → 告诉用户该维度搜索困难，
可能是主题冷门或关键词不对，建议人工调整搜索方向。
```

### 无法判断调研类型
```
无法归类 → 用通用信息收集模式：
1. 直接问用户"你想了解什么方面的信息？"
2. 让用户自己列出关心的维度
3. 按相同流程执行
```

### 搜索结果普遍质量低
```
Phase 5 发现多数维度货物崇拜 → 停止汇总，
告诉用户原始信息源质量不足，summary 会不可靠。
```
