## 元发现

### M1 · 4 次方向纠偏的方法论价值

| 版本 | AI 倾向 | 用户视角 | 教训 |
|------|---------|---------|------|
| v1 | 工业化分工（PM/RD/QA） | "意义不大" | AI 容易复用既有模式，对场景特殊性敏感不足 |
| v2 | 多视角增强 | "Standard 才需要协同" | 边界感不强：把"Lite 增强"误当作"Standard 落地" |
| v3 | 实时信任度累积 | "太复杂" | AI 倾向加机制 |
| v4 | 延迟批量回顾 | 采用 | 用户简化能力是 AI 学不到的 |

**沉淀**：产品定位 / 复杂度 / 场景边界这三类决策，**用户视角永远胜过 AI 视角**。

### M2 · 用户洞察的可贵性

用户两个关键洞察：
- "AI 时代不是切分，是赋能" → 否定了角色分工
- "Standard 是因为复杂度才协同，不是因为人多" → 推翻了"档位 = 人数"
- "延迟批量比实时简单" → 简化了机制

这些洞察 AI 模型很难自主达到——它们建立在"对真实工作场景的体感"上。

→ **加入 backlog/proposals.md**："产品定位 / 复杂度判定 / 场景边界 三类决策必须用户拍板"

### M3 · 协议层 vs 工程层

v1.0.21 是 H-L 首个**纯协议层**改动版本：
- 不修脚本（init / upgrade / uninstall / validate 全部不动）
- 不写代码（无新工具）
- 仅改 markdown 协议（principles + skill body + 模板）

**好处**：
- 改动简单（236 行）
- 风险低（不破坏代码）
- 但**完全依赖 AI 遵循协议**——这是新挑战

→ **沉淀**：H-L 的核心价值是"协议层"，工程层只是承载。这给后续 v1.0.22 / v1.1 设计提供方向：能用协议解决的不动代码。

### M4 · 与 v1.0.20 dogfooding 的对比

- v1.0.20（md-counter 示例项目）：path-a 完整跑通，但是**简单业务**
- v1.0.21（决策学习协议）：path-a 完整跑通，**纯协议层改动**

两次 dogfooding 验证了 path-a 在不同复杂度场景的可用性。
