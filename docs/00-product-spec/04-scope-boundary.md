# 产品边界

> 明确划分Harness-Lite做什么、不做什么。这是避免过度承诺和scope creep的关键。

---

## 一、做什么（核心范围）

### 1.1 核心能力清单

```
✅ 提供AI协作工程化的开箱即用框架
✅ 自动加载团队约定（CLAUDE.md + rules）
✅ 4阶段产物链路（需求→设计→代码→测试）
✅ 路径分级（完整/小需求/Bug修复 三条路径）
✅ 多Agent上下文隔离（主skill + subagent）
✅ 知识库沉淀流水线（schemas + wiki）
✅ hook门禁防护（git/敏感文件/危险命令）
✅ 智能初始化脚本（按团队情况自适应）
✅ 完整的产品文档（安装/使用/演进）
✅ 演进机制（版本管理 + 升级 + 卸载）
```

### 1.2 v1.0 MVP 范围

```
✅ Standard档（Team Small 2-5人）
✅ 3个核心skill（req/design/review）
✅ 4个subagent（doc/reviewer/implementer/validator）
✅ 4阶段产物模板 × 3条路径
✅ 4类schemas（pitfall/decision/interface/architecture）
✅ 基础hook（git push / 敏感文件）
✅ init.sh + validate.sh + uninstall.sh
✅ 1个完整Demo示例
```

### 1.3 v1.1+ 计划扩展

```
v1.1 (规划中):
  - Team Medium档（6-15人）
  - 角色体系（PM/RD/QA分工）
  - 扩展skill（test-cases/wrap/distill）
  - 完整知识蒸馏流水线
  - upgrade.sh

v1.2 (远期):
  - Team Large档（16-30人）
  - 多项目支持
  - 跨项目知识库

v1.3 (远期):
  - Solo Edition（个人版）

v2.0 (远期):
  - 重大重构（基于v1.x反馈）
```

## 二、不做什么（明确边界）

### 2.1 不替代AI编码工具本身

```
❌ 不做IDE插件
❌ 不做AI编辑器（不和Claude Code/Cursor竞争）
❌ 不做模型调用/AI网关
❌ 不做Prompt Engineering优化工具
```

**Harness-Lite是工作流框架，不是AI工具本身。**

### 2.2 不替代项目管理工具

```
❌ 不做任务管理（不和Jira/Linear竞争）
❌ 不做需求管理平台
❌ 不做时间跟踪
❌ 不做团队成员管理
```

**Harness-Lite专注于"AI如何与团队协作"，不管"团队如何管理项目"。**

### 2.3 不替代CI/CD和DevOps

```
❌ 不做构建/部署pipeline
❌ 不做测试自动化平台
❌ 不做监控/告警
❌ 不做基础设施即代码
```

**Harness-Lite是编码侧工具，DevOps是运维侧工具，互补使用。**

### 2.4 不替代Code Review本身

```
❌ 不能保证代码100%没bug
❌ 不能替代架构师的设计决策
❌ 不能解决人的问题（团队不愿意用，无解）
❌ 不能让差代码变好代码
```

**Harness-Lite减少低级错误，但架构级决策仍需人审。**

### 2.5 不做这些AI产品形态

```
❌ 不做大模型本身（不训练模型）
❌ 不做RAG系统
❌ 不做AI Agent平台（不和Dify/Coze竞争）
❌ 不做编程教学产品
```

### 2.6 不强制特定技术栈

```
❌ 不绑定特定语言（Java/Python/JS都支持）
❌ 不绑定特定框架（Spring/Django/Express等）
❌ 不绑定特定测试工具（JUnit/pytest/jest等）
❌ 不绑定特定Git平台（GitHub/GitLab/Gitee）
```

**tech-stack-rules.md由用户根据自己项目定制。**

## 三、灰色地带（明确取舍）

以下是容易引起误会的灰色地带，明确我们的取舍：

### 3.1 关于知识库

```
做什么：
✅ 提供知识库结构（schemas + wiki）
✅ 提供蒸馏流水线（distill skill）
✅ 提供4类基础模板

不做什么：
❌ 不做知识图谱可视化
❌ 不做全文检索引擎
❌ 不做知识库的UI界面
❌ 不存储用户知识（用户的wiki在用户仓库）
```

### 3.2 关于代码生成

```
做什么：
✅ 通过CLAUDE.md约束AI生成的代码
✅ 通过产物链路引导AI按步骤生成

不做什么：
❌ 不直接生成代码（AI做这个）
❌ 不做代码模板/脚手架（init.sh只搭框架，不生代码）
❌ 不做代码补全
```

### 3.3 关于协作

```
做什么：
✅ 提供团队协作的"共识机制"
✅ 通过版本目录支持多人协作

不做什么：
❌ 不做实时协作（不像Google Docs）
❌ 不做评论/讨论功能
❌ 不做权限管理（用git的权限）
```

### 3.4 关于测试

```
做什么：
✅ 提供测试用例模板（04-测试.md）
✅ 强调验收分层（Layer 1/2/3）
✅ 通过路径分级强调"必须测试"

不做什么：
❌ 不做测试框架（用JUnit/pytest）
❌ 不做测试运行器
❌ 不做覆盖率工具
❌ 不做E2E测试工具（推荐Playwright，但不集成）
```

### 3.5 关于自动化

```
做什么：
✅ 提供初始化自动化（init.sh）
✅ 提供升级自动化（upgrade.sh）
✅ 通过hook自动化部分约束

不做什么：
❌ 不做完全无人值守（关键节点必须人介入）
❌ 不做"AI自动决策上线"（最终决策必须人）
❌ 不做工作流引擎（不像Airflow）
```

## 四、扩展性边界

### 4.1 用户可以扩展的

```
✅ 自定义tech-stack-rules（强烈鼓励）
✅ 自定义domain-rules（业务铁律）
✅ 自定义产物模板字段
✅ 自定义subagent行为
✅ 自定义hook
✅ 自定义knowledge-distill的schemas
✅ 自定义version目录命名规则
```

### 4.2 用户不能修改的（核心契约）

```
❌ 4阶段产物链路结构（破坏会导致工具不兼容）
❌ 路径分级的判定逻辑（破坏会导致路径错乱）
❌ subagent的隔离机制（破坏防自写自批保护）
❌ CLAUDE.md的@import机制（破坏自动加载）
❌ 验收分层（Layer 1/2/3）的语义
```

**类比**：你可以改房子的装修（rules/templates），但不能拆承重墙（核心架构）。

### 4.3 扩展插件机制（远期）

```
v2.0+ 计划：
  - 插件机制（第三方贡献skill）
  - 模板市场（行业特定tech-stack-rules）
  - 案例库（最佳实践分享）
```

## 七、版本边界

### 7.1 兼容性承诺

```
PATCH版本 (1.0.x)：完全向后兼容
  - 修bug、改文档
  - 用户升级零成本

MINOR版本 (1.x.0)：向后兼容
  - 新增能力（默认关闭，可选启用）
  - 用户升级时提示diff

MAJOR版本 (x.0.0)：可能破坏兼容
  - 提供迁移工具
  - 至少3个月预告期
```

### 7.2 支持窗口

```
当前版本（latest）：完全支持
前一个MINOR版本：bug修复支持（6个月）
更早版本：仅安全修复（12个月）
���早版本：不支持
```

## 八、Scope Creep防护

为了防止产品功能膨胀，每次新提议必须通过以下4维评估（详见 [proposals.md](../../backlog/proposals.md)）：

```
1. 价值评估（高/中/低）
2. 契合度评估（高/中/低）
3. 集成方式（核心/扩展/可选）
4. 成本评估（人天）

决策矩阵：
- 价值高 + 契合高 + 成本低 → ✅ 立即纳入
- 价值高 + 契合低 → 🤔 考虑做插件
- 价值低 → ❌ 拒绝
- 契合度低（不属于AI协作工程化） → ❌ 拒绝
```

## 九、边界检验清单

每个新功能/新建议进来时，问自己：

```
□ 是否在"做什么"清单内？
□ 是否在"不做什么"清单外？
□ 是否符合4维评估？
□ 是否破坏现有契约？
□ 是否符合"小团队优先"定位？

如果有任一"否"，需要慎重考虑或拒绝。
```

## 十、边界的演进

边界**不是一成不变**，会随版本演进调整：

```
v1.0：当前边界（如本文档）
  ↓
v1.x：可能扩展
  - 加入Solo Edition
  - 加入更多档位
  - 加入扩展skill
  ↓
v2.0：边界可能重新定义
  - 基于v1.x反馈调整
  - 可能引入插件机制
  - 可能调整目标用户范围
```

**每次边界调整都会在CHANGELOG中明确说明。**
