## 使用说明

`tech-stack-rules.md` 治"技术栈陷阱"，**`domain-rules.md` 治"业务陷阱"**。

业务陷阱的特征：
- 不是语法层面的错（语法正确但业务错）
- 通常来自历史踩坑/线上事故
- AI 不读这条规则就会按"通用做法"做错

例如：
- ❌ 通用做法：扣款用乐观锁
- ✅ 本业务必须：扣款用悲观锁（之前出过并发问题）

**这种"业务特有"的约束才放本文件**。

## 三、数据契约

> 在此添加数据契约相关铁律。常见类别：
> - 接口字段的口径定义
> - 跨端字段对齐（DB/Entity/SQL/ResultMap/DTO 五层）
> - 老数据兼容性处理
> - 字段语义（金额单位/时间单位/枚举值）

### 示例规则（待团队替换为实际业务规则）

#### 跨端契约五层落齐
- **要求**：DB / Entity / SQL / ResultMap / DTO 五层字段必须完整对齐
- **反向陷阱**：任一层缺字段 → 前端列空白
- **检查点**：新增字段时
- **示例**：
  ```
  DB:        ALTER TABLE user ADD COLUMN nickname VARCHAR(50);
  Entity:    private String nickname; // ← 必须加
  SQL:       SELECT nickname FROM user; // ← 必须加
  ResultMap: <result column="nickname" property="nickname"/> // ← 必须加
  DTO:       private String nickname; // ← 必须加
  ```

- **要求**：脱敏走 @Desensitize、权限走 @YwAuthMethod 注解
- **反向陷阱**：业务层手写 substring + "****" → mask 不一致

## 添加新规则的工作流

```
线上事故发生
    ↓
事故复盘 → 找出根因
    ↓
判断：是技术栈问题还是业务问题？
    ├── 技术栈问题 → 加到 tech-stack-rules.md
    └── 业务问题 → 加到本文件
    ↓
关联到 team-knowledge/wiki/pitfalls/{编号}-{标题}.md
    ↓
通知团队（在下次站会同步）
    ↓
1个月后 review 该规则是否还需要
```
