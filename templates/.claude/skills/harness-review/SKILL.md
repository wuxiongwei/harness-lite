# /harness-review · 一致性审计 skill

> **核心质量机制**：通过多视角校验暴露翻译失真

---

## 设计哲学

```
"产物链路 = 同一意图的多层翻译"
              ↓
     翻译失真可被机器校验
              ↓
   一致性审计 = 翻译失真校验
```

---

## 触发条件

- 编码完成（03-代码索引.md 状态 = 🟢）
- 测试完成（04-测试.md 状态 = 🟢）
- 用户主动调用 `/harness-review`

## Phase 2：5维度并行审计

### 维度1：需求 ↔ 设计

```
Task(
  subagent_type: "reviewer",
  description: "需求-设计一致性",
  prompt: """
    独立比对 01-需求 和 02-设计：
    
    检查项：
    1. 01-需求每条AC在02-设计中是否有对应实现？
    2. 02-设计是否做了01-需求没要求的事？
    3. 边界场景对齐吗？
    4. "不做的范围"在02-设计中是否仍然守住？
    
    输出：差异清单（如有）
  """
)
```

### 维度2：设计 ↔ 代码

```
Task(
  subagent_type: "reviewer",
  description: "设计-代码一致性",
  prompt: """
    独立比对 02-设计 和 03-代码索引 + git diff：
    
    检查项：
    1. 02-设计的每个决策点都在代码中实现吗？
    2. 代码是否做了02-设计没说的事？
    3. 03-代码索引的"偏差项"是否合理且回写？
    4. 代码是否动了"不做的范围"中的文件？
    
    输出：差异清单
  """
)
```

### 维度3：代码 ↔ 测试

```
Task(
  subagent_type: "reviewer",
  description: "代码-测试一致性",
  prompt: """
    独立比对 03-代码索引 和 04-测试：
    
    检查项：
    1. 所有代码改动都有对应测试吗？
    2. 测试覆盖率是否达红线？
    3. 测试是否真的覆盖代码逻辑（不是为测试而测试）？
    4. Layer 3 是否真实执行（不是单测代替）？
    
    输出：差异清单
  """
)
```

### 维度4：测试 ↔ 需求（反向校验！关键）

```
Task(
  subagent_type: "reviewer",
  description: "测试反推需求",
  prompt: """
    从04-测试反推到01-需求：
    
    检查项：
    1. 从测试用例能反推出01-需求吗？
    2. 01-需求每条AC都有Layer 3覆盖吗？
    3. 测试是否覆盖了01-需求的"边界场景"？
    4. 测试结果（实际值）能证明AC通过吗？
    
    输出：反推一致性报告
  """
)
```

### 维度5：代码 ↔ 规则

```
Task(
  subagent_type: "reviewer",
  description: "代码-规则合规",
  prompt: """
    检查代码是否违反规则：
    
    检查项：
    1. 是否违反 principles.md 中的行为准则？
    2. 是否违反 tech-stack-rules.md 中的技术栈约束？
    3. 是否违反 domain-rules.md 中的业务铁律？
    4. 是否有反向陷阱中提到的"错误写法"？
    
    输出：违规清单（如有）
  """
)
```

### 维度6：AC ↔ 用户路径真验证（v1.0.27 起 · §6.1 用户故事真闭环）

> **来源**：v1.0.27 用户反馈——某次 AI 报"完美！部署已全部完成！"，后端 API / 测试全绿，但**前端没集成**用户实际无法使用。维度1-5 全通过但**用户故事没闭环**。

```
Task(
  subagent_type: "reviewer",
  description: "AC-用户路径真验证",
  prompt: """
    检查每个验收标准（AC）是否真实可被用户走通：
    
    检查项（每条 AC 都要检）：
    1. **用户入口识别**：这个 AC 用户从哪里开始？（哪个页面 / 按钮 / API 端点）
       - 前端功能：按钮在哪？路由注册了？组件集成到页面了？
       - 后端功能：API 端点文档了？调用方集成了？
    
    2. **中间路径识别**：用户点击后发生什么？（前端交互 / 后端调用链）
       - 前端是否真调用了后端 API？
       - 后端是否有对应 router / service？
    
    3. **结果可观测**：用户最终看到什么？（页面变化 / 数据展示 / 通知 / 日志）
    
    4. **端到端联调**：如果涉及前后端，二者是否真集成？
       - 前端组件代码写了但没集成到任何页面 → ❌ 用户无入口
       - 后端 API 通但前端没调 → ❌ 用户走不到
    
    严格判定：
    - ✅ 入口 + 中间路径 + 结果 三者全有真实可走路径 = 通过
    - ❌ 任一缺失 / 只有代码但没集成 / 只有 API 但无前端调用 = 不通过
    
    输出格式：
    | AC | 入口 | 中间路径 | 结果可观测 | 端到端 | 判定 |
    |---|-----|---------|-----------|-------|------|
    | AC1: 用户点击关注按钮 | ❌ 组件代码有但未集成到页面 | - | - | ❌ | **不通过** |
    | AC2: 持仓自动同步 | ✅ cron 任务配置 | ✅ 调用链完整 | ✅ 数据库有记录 | ✅ | **通过** |
    
    高风险关键词（出现这些 = 必须深挖）：
    - "组件代码已写" / "API 已部署" / "测试通过" ← 可能缺集成
    - "后端完成" ← 可能缺前端
    - "前端完成" ← 可能缺路由 / 集成
  """
)
```

**此维度不通过 = P0 阻塞 = 禁止合并**。

## Phase 3.5：决策点处理（v1.0.21+ · principles §13）

遇到决策点（≥ 2 个合理选项）时，按 principles §13 流程：查 auto-decide → 命中自决+标注 / 未命中询问+记 log。

### ⚠️ v1.0.24 强约束（防 M1 实施 gap）

每次必做：AskUserQuestion 调过 / "X 还是 Y" 对比 / AI 自决 N 选 1 → 都要 append decision-log。
详见 principles §13.1.1 / §13.1.2。

**典型决策点（harness-review）**：
- 一致性审计视角数量（3 维 / 5 维）
- 输出粒度（仅差异点 / 完整对比表）
- 分级阈值（红/黄/绿三级 vs 细化五级）

## Phase 4：分级处置

### 全部 🟢 PASS

```
→ 一致性审计通过
→ 提示进入"人介入4：最终决策"
→ 等待人决策是否commit/上线
```

### 任一 🟡 REVISION

```
→ 列出所有需要修订的项
→ 给出修订建议（如何修订到一致）
→ 委托对应 subagent 修订
→ 修订后重新审计
```

### 任一 🔴 BLOCKED

```
→ 输出阻塞原因
→ 严重项必须修，重要项是否defer由人决策
→ 等待人介入
```

## 关键原则

### 反向同步

```
当发现"代码做了但01-需求没说"：
  ↓
判断这个功能是否合理：
  ├── 合理 → 反向同步：补充到01-需求.md
  └── 不合理 → 立即删除/回退代码
  
绝不能默认"代码为准"！
```

### 阻塞即停止

```
发现以下情况立即停止，不允许放行：

1. Layer 3 未真实执行
2. 测试用例与01-需求 AC 不对齐
3. 代码动了"不做的范围"
4. 违反 domain-rules.md 的硬性铁律
5. 单测假通过（mock数据掩盖问题）
```
