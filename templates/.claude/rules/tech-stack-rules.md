## 使用说明

1. 本文件由 init.sh 根据**自动扫描的项目技术栈**预填
2. 可以根据团队实际情况调整、补充、删减
3. 每条规则建议给出"反向陷阱"，让 AI 知道"不这么做会出什么问题"
4. 规则不要太多，控制在 **15-30条**为宜（太多 AI 会挑选性遵守）

## 一、{{LANGUAGE_BACKEND}} 后端约束

> 由 init.sh 根据项目检测自动填充。常见示例如下：

### 示例：Java + Spring Boot 2.x

#### 1. 禁用record类型
- **要求**：用传统 class + getter/setter
- **反向陷阱**：JDK版本不支持 record（项目用 JDK8）
- **示例**：
  ```java
  // ❌ 错误
  public record User(String name, Integer age) {}
  
  // ✅ 正确
  public class User {
      private String name;
      private Integer age;
      // getter/setter
  }
  ```

#### 2. 日期处理统一用 java.time
- **要求**：禁止 Date 与 LocalDateTime 混用
- **反向陷阱**：时区处理混乱、序列化不一致
- **示例**：
  ```java
  // ❌ 错误
  Date now = new Date();
  
  // ✅ 正确
  LocalDateTime now = LocalDateTime.now();
  ```

#### 3. 异步注解用 @Async
- **要求**：禁止手工 new Thread / new Runnable
- **反向陷阱**：线程池失控、资源泄漏

#### 4. 数据库事务必加 @Transactional(rollbackFor = Exception.class)
- **要求**：默认 Spring 只回滚 RuntimeException，必须显式声明
- **反向陷阱**：Checked Exception 不回滚导致数据不一致

#### 5. 敏感字段必加脱敏注解
- **要求**：身份证/手机号/姓名 字段必须 @Desensitize
- **反向陷阱**：日志/接口直接暴露敏感信息

## 二、{{LANGUAGE_FRONTEND}} 前端约束

> 由 init.sh 根据项目检测自动填充。常见示例如下：

### 示例：Vue 2.6

#### 1. 禁用 Vue 3 语法
- **要求**：不能用 Composition API / setup() / ref() 等
- **反向陷阱**：当前版本不支持，运行时报错
- **示例**：
  ```javascript
  // ❌ 错误（Vue 3）
  import { ref } from 'vue'
  setup() { const count = ref(0) }
  
  // ✅ 正确（Vue 2）
  data() { return { count: 0 } }
  ```

#### 2. UI 组件库统一
- **要求**：用 {{UI_LIBRARY}}（如 Element UI），不要混用其他组件库
- **反向陷阱**：打包体积膨胀、样式冲突

#### 3. 状态管理用 Vuex
- **要求**：跨组件状态走 Vuex，禁止 props 层层传递
- **反向陷阱**：组件耦合度高、维护成本指数上升

#### 4. 路由守卫统一在 router/index.js
- **要求**：不要分散到各组件
- **反向陷阱**：守卫逻辑重复、跳转混乱

## 三、{{DATABASE}} 数据库约束

> 由 init.sh 根据项目检测自动填充。常见示例如下：

### 示例：MySQL 5.7

#### 1. DDL 走 DBA 审批
- **要求**：CREATE TABLE / ALTER TABLE 不在代码中执行
- **反向陷阱**：未经审批的 DDL 上线导致兼容性问题

#### 2. 索引命名规范
- **要求**：`idx_{表名}_{字段名}`
- **反向陷阱**：索引重复、命名混乱

#### 3. 禁止 SELECT *
- **要求**：必须明确列出字段
- **反向陷阱**：表结构变更影响应用、传输数据冗余

#### 4. 分页参数统一
- **要求**：用 pageNum + pageSize（不用 offset+limit）
- **反向陷阱**：跨模块对接时参数不一致

## 四、API 规范

#### 1. RESTful 风格
- **要求**：GET/POST/PUT/DELETE 语义正确
- **反向陷阱**：用 GET 做修改、用 POST 做查询

#### 2. 统一返回结构
- **要求**：`{code, message, data}` 三段式
- **反向陷阱**：错误处理不一致、前端解析复杂

#### 3. 接口幂等性
- **要求**：写操作必须幂等（防重复提交）
- **反向陷阱**：网络抖动导致重复扣款/重复创建

---

## 五、Git 规范

#### 1. Commit Message 格式
- **要求**：`<type>: [模块名] <subject>`
- **反向陷阱**：历史难追溯、CHANGELOG难生成
- **示例**：
  ```
  feat: [user-center] 新增手机号注册
  fix: [order] 修复并发扣款重复
  ```

#### 2. 分支命名规范
- **要求**：`feature/`、`bugfix/`、`hotfix/` 前缀
- **反向陷阱**：分支管理混乱

#### 3. 不直推保护分支
- **要求**：main / master 必须走 PR
- **反向陷阱**：未经 review 代码进主线

## 六、构建与依赖

#### 1. 依赖必须明确版本
- **要求**：禁止使用 `latest`、`*` 等浮动版本
- **反向陷阱**：构建结果不可重现

#### 2. 不引入未审核的新依赖
- **要求**：新增依赖必须团队评审
- **反向陷阱**：依赖膨胀、安全风险、license冲突

---

## 七、测试约束

#### 1. 验收分层标注
- **要求**：测试必须明确标注 Layer 1/2/3
- **反向陷阱**：用单测充作 E2E，"假通过"上线

#### 2. 单测覆盖率红线
- **要求**：核心模块单测覆盖率 ≥ 70%
- **反向陷阱**：核心逻辑改动无防护

#### 3. E2E 必须覆盖主流程
- **要求**：用户主链路必须有 E2E 测试
- **反向陷阱**：上线前最后才发现链路问题

---

## 八、性能与安全

#### 1. 数据库查询限制
- **要求**：禁止 N+1 查询，禁止全表扫描
- **反向陷阱**：性能急剧下降

#### 2. 敏感信息处理
- **要求**：日志中敏感字段必须脱敏
- **反向陷阱**：日志泄露隐私

#### 3. SQL 注入防护
- **要求**：必须用参数化查询，禁止字符串拼接 SQL
- **反向陷阱**：SQL 注入漏洞
