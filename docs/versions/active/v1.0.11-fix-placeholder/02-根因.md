## 2. 根因的根因

### 2.1 "添加新占位符"的开发协议缺失

每加一个新 `{{...}}` 模板变量，**正确的工作流**应该是：
1. 模板文件加 `{{...}}`
2. `init.sh::render_template_vars` 加对应 sed 规则
3. `upgrade.sh` 渲染段也加（如果文件会被 upgrade 覆盖）
4. validate.sh 测试一次"残留扫描"

但实际上只做了步骤 1。**和 v1.0.5/v1.0.7 schema 漂移完全同根**：单点修改没引发横向更新。

### 2.2 v1.0.6/1.0.7 的自检体系覆盖不全

v1.0.6 加 settings.json schema 自检 → v1.0.7 扩展到 skill/agent → 但**没扩展到模板变量渲染**。tech-stack-rules.md 那个特例检查是 v1.0.5 之前就在的，没人把它一般化。

### 2.3 upgrade.sh 设计时的盲区

v1.0.9 设计 upgrade.sh 时考虑了 tech-stack-rules.md（已渲染实例不能覆盖），但**漏了 domain-rules.md**——这个文件也是 init 时渲染过的，但 upgrade 时既覆盖了又没重新渲染。

→ 设计阶段没把"哪些文件是模板版 / 哪些是实例版 / upgrade 时如何处理"系统化。

---

## 3. 修复方案

### 3.1 主修 · init.sh 加 `{{HARNESS_LITE_DOCS_URL}}` 渲染

```bash
local docs_url="https://github.com/zoe/harness-lite/blob/main/README.md"
sed -i.bak ... -e "s#{{HARNESS_LITE_DOCS_URL}}#$docs_url#g" ...
```

### 3.2 主修 · upgrade.sh 覆盖 rules 后立即渲染

```bash
# 覆盖完 rules 后，渲染版本占位符
for rendered in ".claude/rules/principles.md" ".claude/rules/domain-rules.md"; do
    sed -i.bak \
        -e "s#{{HARNESS_LITE_VERSION}}#$NEW_VERSION#g" \
        -e "s#{{INSTALL_DATE}}#$upgrade_date#g" \
        "$rendered"
done
```

### 3.3 横向预防 · validate.sh 全量扫描

```bash
# 不再只检查 tech-stack-rules.md，全量扫 CLAUDE.md + rules/*.md
unrendered=$(grep -lE "\{\{[A-Z_]+\}\}" CLAUDE.md .claude/rules/*.md 2>/dev/null)
if [ -n "$unrendered" ]; then
    echo "✗ 以下文件含未渲染占位符："
    # 列出每个文件和具体占位符
fi
```

任何未来加新占位符忘了同步 init.sh，下一次跑 validate.sh **立刻被抓到**。

### 3.4 现场修 · stock_make_money

- `CLAUDE.md` → sed 渲染 `{{HARNESS_LITE_DOCS_URL}}`
- `.claude/rules/domain-rules.md` → sed 渲染 2 个变量

### 3.5 不做（避免过度治理）

- ❌ 不引入"模板变量声明文件"统一管理（设计开销大）
- ❌ 不在 install/upgrade 加事后扫描兜底（让 validate.sh 兜，避免主流程膨胀）
