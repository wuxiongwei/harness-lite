# /harness:review · 一致性审计 skill

> **核心质量机制**：通过多视角校验暴露翻译失真

---

## 设计哲学

```
"产物链路 = 同一意图的多层翻译"
              ↓
     翻译失真可被机器校验
              ↓
   一致性审计 = 翻译失真校验
```

---

## 触发条件

- 编码完成（03-代码索引.md 状态 = 🟢）
- 测试完成（04-测试.md 状态 = 🟢）
- 用户主动调用 `/harness:review`

---

## Phase 1：上下文加载（5路并行）

并行 Read 5份产物：

```
1. 01-需求.md
2. 02-设计.md
3. 03-代码索引.md
4. 04-测试.md
5. git diff （实际代码改动）
```

---

## Phase 2：5维度并行审计

### 维度1：需求 ↔ 设计

```
Task(
  subagent_type: "reviewer",
  description: "需求-设计一致性",
  prompt: """
    独立比对 01-需求 和 02-设计：
    
    检查项：
    1. 01-需求每条AC在02-设计中是否有对应实现？
    2. 02-设计是否做了01-需求没要求的事？
    3. 边界场景对齐吗？
    4. "不做的范围"在02-设计中是否仍然守住？
    
    输出：差异清单（如有）
  """
)
```

### 维度2：设计 ↔ 代码

```
Task(
  subagent_type: "reviewer",
  description: "设计-代码一致性",
  prompt: """
    独立比对 02-设计 和 03-代码索引 + git diff：
    
    检查项：
    1. 02-设计的每个决策点都在代码中实现吗？
    2. 代码是否做了02-设计没说的事？
    3. 03-代码索引的"偏差项"是否合理且回写？
    4. 代码是否动了"不做的范围"中的文件？
    
    输出：差异清单
  """
)
```

### 维度3：代码 ↔ 测试

```
Task(
  subagent_type: "reviewer",
  description: "代码-测试一致性",
  prompt: """
    独立比对 03-代码索引 和 04-测试：
    
    检查项：
    1. 所有代码改动都有对应测试吗？
    2. 测试覆盖率是否达红线？
    3. 测试是否真的覆盖代码逻辑（不是为测试而测试）？
    4. Layer 3 是否真实执行（不是单测代替）？
    
    输出：差异清单
  """
)
```

### 维度4：测试 ↔ 需求（反向校验！关键）

```
Task(
  subagent_type: "reviewer",
  description: "测试反推需求",
  prompt: """
    从04-测试反推到01-需求：
    
    检查项：
    1. 从测试用例能反推出01-需求吗？
    2. 01-需求每条AC都有Layer 3覆盖吗？
    3. 测试是否覆盖了01-需求的"边界场景"？
    4. 测试结果（实际值）能证明AC通过吗？
    
    输出：反推一致性报告
  """
)
```

### 维度5：代码 ↔ 规则

```
Task(
  subagent_type: "reviewer",
  description: "代码-规则合规",
  prompt: """
    检查代码是否违反规则：
    
    检查项：
    1. 是否违反 principles.md 中的行为准则？
    2. 是否违反 tech-stack-rules.md 中的技术栈约束？
    3. 是否违反 domain-rules.md 中的业务铁律？
    4. 是否有反向陷阱中提到的"错误写法"？
    
    输出：违规清单（如有）
  """
)
```

## Phase 4：分级处置

### 全部 🟢 PASS

```
→ 一致性审计通过
→ 提示进入"人介入4：最终决策"
→ 等待人决策是否commit/上线
```

### 任一 🟡 REVISION

```
→ 列出所有需要修订的项
→ 给出修订建议（如何修订到一致）
→ 委托对应 subagent 修订
→ 修订后重新审计
```

### 任一 🔴 BLOCKED

```
→ 输出阻塞原因
→ 严重项必须修，重要项是否defer由人决策
→ 等待人介入
```

---

## 关键原则

### 反向同步

```
当发现"代码做了但01-需求没说"：
  ↓
判断这个功能是否合理：
  ├── 合理 → 反向同步：补充到01-需求.md
  └── 不合理 → 立即删除/回退代码
  
绝不能默认"代码为准"！
```

### 阻塞即停止

```
发现以下情况立即停止，不允许放行：

1. Layer 3 未真实执行
2. 测试用例与01-需求 AC 不对齐
3. 代码动了"不做的范围"
4. 违反 domain-rules.md 的硬性铁律
5. 单测假通过（mock数据掩盖问题）
```
