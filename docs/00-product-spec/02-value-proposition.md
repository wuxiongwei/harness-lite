# 价值主张

> 装了Harness-Lite，你的团队能得到什么？这是产品的核心承诺。

---

## 一、一句话承诺

**让你2-5人的小团队，在30分钟内建立起AI协作共识，1周内见效，1个月内沉淀团队资产。**

---

## 二、5大核心价值

### 价值1：AI产出质量稳定（不再"自由发挥"）

#### 你现在的痛点
```
😵 同一个需求，张三和李四问AI，写出来的代码风格完全不一样
😵 AI总是用项目不支持的语法（如Java record / Vue 3 Composition API）
😵 AI偷偷加了未要求的功能，事后才发现
😵 AI忽略团队约定的规则，每次都要重复纠正
```

#### Harness-Lite的解法
```
✅ CLAUDE.md自动加载技术栈规则，AI每次会话都"知道"约束
✅ tech-stack-rules.md明令禁止/允许的语法，AI不能自由发挥
✅ "外科手术式改动"原则，AI不主动加未要求的功能
✅ principles.md行为准则，从根本上约束AI的行为模式
```

#### 量化收益
- AI代码返工率下降 **50%+**
- 因AI跑偏导致的bug数下降 **40%+**
- 团队Code Review时间下降 **30%+**

---

### 价值2：上下文不再"健忘"

#### 你现在的痛点
```
😵 每次开新会话都要重新解释项目背景，浪费15分钟
😵 项目越大，AI越容易"忘记"之前的约定
😵 跨会话工作时，AI对项目的理解时好时坏
😵 团队新人加入，AI对TA和老员工"区别对待"
```

#### Harness-Lite的解法
```
✅ CLAUDE.md每次会话自动加载（@import机制）
✅ 项目地图、技术栈、团队约定一次性灌注给AI
✅ 知识库按需Read，避免主上下文过载
✅ subagent隔离机制，跨3个文件的探索委托给subagent
```

#### 量化收益
- 单次会话启动到能干活的时间从 **15分钟 → 2分钟**
- 跨会话需要重复解释的次数下降 **80%+**
- 新人首次AI协作的成功率提升 **60%+**

---

### 价值3：产物链路可追溯（不再"代码即一切"）

#### 你现在的痛点
```
😵 代码写完了，但需求理解错了——返工
😵 测试覆盖了，但漏了边界场景——上线翻车
😵 改了一个地方，影响了另一个——回归bug
😵 半年后回头看：当时为啥这么设计？没人记得
```

#### Harness-Lite的解法
```
✅ 4阶段产物链路：01需求 → 02设计 → 03代码 → 04测试
✅ 每阶段反向校验：从下游反推上游一致性
✅ 路径分级：完整需求走4阶段，小需求走2阶段，Bug专项流程
✅ 决策追溯：02-设计.md里写"为什么这么选"
```

#### 反向校验示例
```
写完04-测试后，AI自动追问：
- "这些测试用例能覆盖01-需求的所有验收标准吗？"
- "如果测试通过，能反推出01-需求被实现了吗？"
- "有没有需求里没写但代码做了的'额外功能'？"
```

#### 量化收益
- 需求理解偏差导致的返工下降 **60%+**
- 测试覆盖率提升 **20%+**（因为反向校验逼着补全）
- 半年后的"代码考古"成本下降 **70%+**

### 价值4：团队知识不流失

#### 你现在的痛点
```
😵 同一个坑，半年内团队踩过3次（没人记得是怎么解决的）
😵 老员工离职后，"为什么这么设计"的原因失传
😵 新人onboarding要1个月（要翻几年前的飞书文档）
😵 跨团队约定散落在各种聊天记录里，没人维护
```

#### Harness-Lite的解法
```
✅ team-knowledge双wiki（biz + tech），结构化沉淀
✅ knowledge-distill流水线：raw素材 → wiki蒸馏
✅ 4类schemas（pitfall/decision/interface/architecture）
✅ 每个需求收尾时，强制提示"有什么值得沉淀"
```

#### 沉淀什么、不沉淀什么
```
✅ 该沉淀：
   - 为什么这么设计（决策原因）
   - 踩过的坑及根因
   - 跨团队约定/口径
   
❌ 不沉淀：
   - 代码本身（看代码就行）
   - 接口文档（看Swagger）
   - 容易过期的状态信息
```

#### 量化收益
- 同类bug重复发生率下降 **70%+**
- 新人onboarding时间从 **1个月 → 2周**
- 关键决策追溯时间从 **2小时 → 5分钟**

### 价值5：危险操作有门禁

#### 你现在的痛点
```
😵 AI执行了rm命令，删了重要文件
😵 AI偷偷push到了主分支
😵 AI编辑了.env文件，差点泄露密钥
😵 AI跳过了pre-commit hook
```

#### Harness-Lite的解法
```
✅ hook机制 + settings.json权限白名单
✅ git push默认拦截，必须人工确认
✅ 敏感文件（.env/credentials.json）禁编辑
✅ 危险命令（rm -rf）禁执行
✅ 阻塞即停止原则：发现阻塞不能解释为"后续依赖"
```

#### 三重防护
```
软约束（铁律）── 写在principles.md，AI主动遵守
   ↓
硬拦截（hook）── 工具调用前自动拦截
   ↓
闸门（guard）── 关键节点强制人工确认
```

#### 量化收益
- 因AI误操作导致的事故 **归零**
- 团队对AI的信任度提升（敢用敢委派）
- 减少"事后救火"的精神消耗

## 三、特色价值（区别于其他方案）

### 特色1：路径分级（不是所有需求都走完整流程）

```
完整需求（30-90分钟）：
  01-需求 → 02-设计 → 03-代码 → 04-测试

小需求（5-15分钟）：
  01-小记 → 04-验证
  
Bug修复（15-60分钟）：
  复现 → 根因 → 修复 → 回归
```

**避免"小需求也写PRD"的过度工程化**。

### 特色2：多Agent上下文隔离（防AI自写自批）

```
主skill (harness-req)
  ├── doc-generator subagent（写文档，不读实现代码）
  ├── reviewer subagent（独立评审，不看doc-generator输出）
  ├── implementer subagent（编码，受约束）
  └── validator subagent（独立环境验证）
```

**每个subagent严格限定可见范围，杜绝"自己写测试自己通过"**。

### 特色3：验收分层（不强制但强烈推荐E2E）

```
Layer 1 单元测试    ← 推荐，但不是终判
Layer 2 集成测试    ← 推荐，但不是终判  
Layer 3 E2E真实链路 ← 强烈推荐（唯一真终判）
```

**禁止用"单测过了"代替"上线前验证"**。

## 五、价值边界（不能给项目带来什么）

为了避免过度承诺，明确**不能**做到的：

```
❌ 不能让差代码变好代码
   → AI产出质量取决于上下文质量，本产品只是放大器

❌ 不能替代Code Review
   → 本产品减少低级错误，但架构级问题仍需人审

❌ 不能让团队立即接受
   → 需要1-2周适应期 + 持续推广

❌ 不能解决人的问题
   → 如果团队不愿意写需求文档，产品再好也用不起来

❌ 不能保证100%消除bug
   → 只能降低bug率，不能消除

❌ 不能跨编程语言魔法
   → 需要根据你的技术栈定制tech-stack-rules.md
```
