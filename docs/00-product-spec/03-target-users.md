# 目标用户

> 谁应该用Harness-Lite？谁不应该？以及我们和其他方案的对比。

---

## 一、目标用户画像（核心受众）

### 1.1 一句话画像

**2-5人的小团队，正在用AI辅助编码，已经感觉到协作问题，但还没复杂到需要重型方案。**

### 1.2 典型代表

#### 画像A：技术合伙人型创业团队
```
团队规模：2-3人
角色构成：1-2个全栈 + 1个产品/设计
现状：
  - 用Claude Code/Cursor做主力开发
  - 节奏快、决策快
  - 痛点：AI产出"看人下菜"，张三的代码和李四的代码风格完全不一样
  - 想要：30分钟能落地的轻量规范
```

#### 画像B：大公司内部敏捷小队
```
团队规模：4-6人
角色构成：3-4个开发 + 1个PM + 1个QA
现状：
  - 大公司有标准（CMMI/工程化），但太重
  - 自己想要小队内的快速迭代规范
  - 痛点：用大公司方案太累，不用又怕失控
  - 想要：可定制的轻量框架
```

#### 画像C：技术工作室/外包小团队
```
团队规模：3-5人
角色构成：技术为主，业务接客户
现状：
  - 同时做多个客户项目，每个项目不一样
  - 不能为每个项目定制重流程
  - 痛点：跨项目复用的最佳实践沉淀不下来
  - 想要：开箱即用 + 可裁剪
```

### 1.3 共同特征

```
✅ 团队规模：2-5人（核心）
✅ 工作方式：高度依赖AI辅助编码（Claude Code/Cursor等）
✅ 痛点共识：已经感觉到协作问题，愿意投入解决
✅ 决策模式：扁平协作，决策链短
✅ 学习意愿：愿意花半天到一天学习新工具
✅ 容忍度：能接受短期投入换长期收益
```

## 三、不是我们的用户

### ❌ 大企业完整团队（30+人）

```
为什么不适合：
- Harness-Lite太轻，无法承载多项目+多角色复杂度
- 应该用 PSC Harness 这类完整方案

如果你是这种团队：
→ 推荐参考：KS-AI-READY (psc-team-harness)
```

### ❌ 不用AI辅助编码的团队

```
为什么不适合：
- 本产品的核心价值是"约束AI"
- 如果团队不用AI，价值大打折扣

替代建议：
→ 用传统工程化方案（DevOps/Scrum等）
```

### ❌ 完全不愿改变工作方式的团队

```
为什么不适合：
- Harness-Lite需要团队主动接受
- 强行推行只会徒增反感

判断标准：
- 团队是否愿意尝试新工具？
- 是否有1-2个推动者？
- 老板是否支持试点？

如果以上Yes < 2个，不建议引入。
```

### ❌ 期望"装上就完美"的团队

```
为什么不适合：
- Harness-Lite是脚手架，需要团队定制
- 不维护的话价值会快速衰减

需要持续投入：
- 每周1小时维护（knowledge-distill + 调整规则）
- 每月review一次CLAUDE.md
```

## 四、决策清单：你应该用Harness-Lite吗？

打分（每条1分），≥6分推荐使用：

```
团队特征
[ ] 团队规模在 2-5 人
[ ] 主要使用AI辅助编码工具（Claude Code/Cursor等）
[ ] 团队有协作痛点（AI跑偏/规范不统一/知识流失）

意愿层面
[ ] 至少有1个人愿意推动落地
[ ] 老板/leader支持试用
[ ] 团队愿意花0.5-1天学习新工具

技术层面
[ ] 项目代码在git仓库管理
[ ] 团队有基本的工程化意识（写PRD、Code Review等）

期望层面
[ ] 接受"短期投入换长期收益"
[ ] 接受"先简单后扩展"的演进路径
[ ] 愿意持续维护（每周1小时）
```

**如果 ≥ 6/9 分，强烈推荐试用。**
**如果 ≤ 4/9 分，建议先解决前置问题。**

## 五、竞品对比（区别于其他方案）

### 5.1 和大公司Harness方案对比

| 维度 | PSC Harness（大公司） | Harness-Lite（小团队） |
|-----|--------------------|-------------------|
| 目标用户 | 30+人产研团队 | 2-5人小团队 |
| Skill数量 | 38个 | 3个核心 + 4 subagent |
| 角色数量 | 19个 | 0（小团队不分角色） |
| 工序复杂度 | 7工序25活动 | 4阶段 + 路径分级 |
| 知识库 | 三层（L0/L1/L2） | 双层（L0 + L1精简） |
| 安装时间 | 1-3小时 | 5-30分钟 |
| 学习成本 | 1-3天 | 半天 |
| 适用场景 | 多项目、多角色、规模化 | 小团队、单/少项目、敏捷 |

**核心差异**：完整 vs 轻量。

### 5.2 和TDD专项方案对比

| 维度 | AI-TDD-Harness | Harness-Lite |
|-----|---------------|--------------|
| 定位 | TDD垂直专项 | 通用协作框架 |
| 阶段数 | 13阶段（路径A） | 4阶段（路径A） |
| Agent数 | 6个独立agent | 4个subagent |
| 验收 | 强制Layer 3 E2E | 推荐Layer 3（不强制） |
| 适用场景 | 严格TDD开发 | 各种开发场景 |
| 路径分级 | A/B/C 3条 | A/B/C 3条 ✅ |
| 上下文隔离 | 是 ✅ | 是 ✅ |

**核心差异**：专项 vs 通用。Harness-Lite借鉴了TDD-Harness的精华（路径分级+上下文隔离），但定位更广。

### 5.3 和编辑器内置规则对比

| 维度 | .cursorrules / .github/copilot | Harness-Lite |
|-----|-----------------------------|--------------|
| 解决问题 | 代码风格统一 | 完整工程化协作 |
| 内容范围 | 代码层面 | 流程+知识+协作 |
| 生命周期 | 编码时 | 全工序（需求→上线） |
| 知识沉淀 | 无 | 有（双wiki） |
| 团队协作 | 弱 | 强 |
| 演进机制 | 无版本管理 | 有完整演进体系 |

**核心差异**：点 vs 面。Harness-Lite是"系统"，不是"规则集"。

### 5.4 和企业DevOps平台对比

| 维度 | GitLab/Jenkins/Argo | Harness-Lite |
|-----|--------------------|--------------|
| 解决问题 | CI/CD自动化 | AI协作工程化 |
| 关注点 | 部署、监控、运行 | 编码、协作、沉淀 |
| AI友好度 | 低（流程刚性） | 高（专为AI设计） |
| 适用阶段 | 上线及之后 | 编码及之前 |
| 关系 | **互补，不冲突** | **互补，不冲突** |

**核心差异**：编码侧 vs 运维侧。两者**互补使用**。

## 六、目标用户的"三类典型场景"

理解你的团队属于哪一类，对正确使用Harness-Lite很重要：

### 场景A：从0到1新团队
```
特征：刚组建，没有历史包袱
推荐路径：
  Day 1: 装好Harness-Lite
  Day 2: 团队启动会 + 跑通Demo
  Day 3: 第一个真实需求走完整流程

注意：
  - 不要追求一开始就完美
  - 让规则跟着实战长出来
```

### 场景B：老团队改造
```
特征：已有项目，已有协作习惯
推荐路径：
  Week 1: 先在2-3人小组试点
  Week 2-3: 跑1-2个真实需求验证
  Week 4: 团队推广 + 制定规范

注意：
  - 老代码不强制走新流程（避免阻力）
  - 新需求强制走（建立新习惯）
  - 给老员工"逐步过渡"的时间
```

### 场景C：跨团队推广
```
特征：你团队用得好，想推广到其他团队
推荐路径：
  Phase 1: 你团队跑3个月，形成成熟案例
  Phase 2: 找1个友好团队试点（不强推）
  Phase 3: 沉淀"行业特定规则"扩展包
  Phase 4: 形成跨团队最佳实践

注意：
  - 每个团队的tech-stack-rules不同，要定制
  - 不要"一刀切"推同一套规则
```

## 七、用户成功路径

```
[L0 发现]     听说有这么个产品
    ↓
[L1 评估]     看完README + 价值主张，决定试试   (< 30分钟)
    ↓
[L2 安装]     init.sh装好                       (< 30分钟)
    ↓
[L3 试用]     跑通示例项目                      (< 1小时)
    ↓
[L4 落地]     在真实项目上跑1个需求             (< 1天)
    ↓
[L5 推广]     在团队中推广                      (1-2周)
    ↓
[L6 沉淀]     形成团队资产（wiki + 自定义规则）  (1-3个月)
    ↓
[L7 推荐]     愿意推荐给其他团队
```

**Harness-Lite的目标**：让 90%+ 的目标用户能从 L0 走到 L4。
