# `/harness-design` 用户手册

> 设计阶段 skill · 把需求翻译为技术方案。

---

## 一句话定位

**path-a 阶段 2** —— 基于 01-需求.md 生成 02-设计.md，含技术方案 / 关键决策表 / 影响面 / 风险。

---

## 何时用

| 场景 | 是否用 |
|-----|-------|
| path-a 走完阶段 1（01-需求 通过）| ✅ 进入阶段 2 |
| path-b 小需求 | ❌ 不用（直接实施）|
| path-c bug 修复 | ❌ 不用（走 02-根因 / 03-修复）|
| 不写代码就想理清思路 | ✅ 设计文档本身就有价值 |

---

## 调用方式

```bash
# 通常在 /harness-req 走完 path-a 阶段 1 后调用
/harness-design

# 或显式指定版本目录
/harness-design --version=v0.x-搜索功能
```

## 输出范例

```
✅ 已读 01-需求.md（用户故事 4 个 / AC 12 条 / 不做范围 5 项）
✅ 已生成 02-设计.md
   - 总体架构（含数据流图）
   - 关键决策 D1-D5（带选项对比 + 选择 + 理由）
   - 接口设计（API / 数据结构）
   - 算法核心
   - 异常处理
   - 测试策略
   - 性能考量
   - 风险与缓解

⏳ 等待人介入 2：设计评审
   评审通过后进入阶段 3 编码
```

## 02-设计.md 结构概览

```
1. 总体架构（模块划分 / 数据流）
2. 关键决策（表格：选项对比）  ← v1.0.21 决策学习协议会问你
3. 模块设计
4. 接口设计
5. 异常处理
6. 测试设计
7. 性能考量
8. 兼容性
9. 风险与缓解
10. 实施清单（给阶段 3 用）
11. 审查清单
```

## 决策点（v1.0.21+）

| 决策点 | 选项示例 |
|-------|---------|
| 表格格式 | Markdown 表 / HTML 表 / 列表 |
| 模块拆分粒度 | 拆子模块 / 单文件 |
| 关键决策表样式 | 横表 / 竖表 |
| 技术方案数量 | 1 方案 / 2-3 备选方案对比 |
| 设计图是否需要 | 文字描述 / ASCII 图 / 链接外部图 |

> 这些决策一旦你授权（详见 `00-decision-learning-guide.md`），下次走 path-a 时 AI 自动用相同选择。

## 常见问题

### Q1：我已有设计草稿，能让 AI 整理而不是重写吗？
A：能。"基于我下面的草稿生成 02-设计.md：<草稿>"。

### Q2：设计评审不通过怎么办？
A：在 02-设计.md 标 🟡 REVISION，写明问题。AI 会修订对应段落。

### Q3：阶段 3 编码时发现设计错了？
A：**反向同步**回 02-设计.md。这是产品核心机制（principles §9）。

### Q4：能跳过设计直接编码吗？
A：path-a **不建议**（设计是 path-a 价值所在）。如果场景简单 → 用 path-b。

### Q5：关键决策表 D1-D5 这种格式必须吗？
A：是 path-a 02-设计.md 的标准段落，**强烈建议保留**——后续复盘 / 一致性审计都会用到。
