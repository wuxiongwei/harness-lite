## 3. 模块设计

### 3.1 协议层 · principles.md §14（新增）

```markdown
## 14. 多人协同协议（v1.0.23 起 · Standard 协同机制）

### 14.1 协同 ≠ 分工

H-L 不做工业化分工（PM 只能调 req / RD 只能调 design）。
而是给"多人在同一项目并行工作"的基础设施。

### 14.2 三类协同问题与对策

| 问题 | 对策 | 文件 |
|-----|------|------|
| 并行不冲突 | 分支策略 + 任务认领 + 冲突预警 | branch-strategy / assignments |
| 责任不重复 | 任务 owner 字段 + 多 owner 支持 | assignments |
| 角色协同 | 协同视角段（4 skill 接入） | 主产物末尾 |

### 14.3 关键文件（团队共享，入仓库）

- `.claude/branch-strategy.md` —— 分支命名 + 主分支保护 + 合并规则
- `.claude/assignments/<姓名>.md` —— 个人任务认领板（claim/进行中/已完成）

### 14.4 软约束原则

所有协同检查**软提醒不阻塞**（不动 git hook）：
- 命名违规 → 提醒
- 任务冲突 → 提醒 + 二次确认
- 文件交叉 → 报告中标 ⚠️

### 14.5 与铁律的优先级

协同协议 < principles §1-§13 铁律。
```

### 3.2 数据层 · 文件 schema

#### `.claude/branch-strategy.md`

```markdown
# 分支策略（团队约定）

## 命名规范
- feat/<short-name>          # 新功能
- fix/<short-name>           # bug 修复
- refactor/<short-name>      # 重构
- docs/<short-name>          # 文档
- chore/<short-name>         # 杂项

## 主分支保护
- main：禁止直推（需 PR）
- develop：仅 lead 可推

## 合并规则
- 必须经过至少 1 人 review
- 必须通过 pre-commit hook
- 推荐 squash merge（保持历史干净）

## 示例
- ✅ feat/user-search-by-email
- ✅ fix/login-500-on-empty-password
- ❌ alice-new-feature（缺类型前缀）
- ❌ feature/search（用 feat 不用 feature）

---

> 团队按需修改本文件。
> AI 在 commit/push 时会按本文件检查分支名（软提醒，不阻塞）。
> 不存在本文件时，AI 跳过检查（向下兼容 v1.0.22）。
```

#### `.claude/assignments/<姓名>.md`

```markdown
# 任务认领（zoe）

## 进行中（claimed）

### v1.0.23-standard-collaboration
- claim 时间：2026-06-18 09:00
- 状态：阶段 2 设计中
- 影响文件：principles.md / 5 skill / .claude/branch-strategy.md / .claude/assignments/...

## 待办（pending）

- v1.0.24-knowledge-share · 待 v1.0.23 完成

## 已完成（done）

### v1.0.21-lite-automation
- 完成时间：2026-06-18
- 协作者：（如有）
```

**字段语义**：
- "进行中"：当前 claim，AI 检测冲突时主要查这段
- "待办"：未来计划
- "已完成"：归档（D2 决策——同文件 done 段，不单独归档文件）
- "影响文件"：可选，给 A3 冲突预警提供精确锚点

### 3.3 流程层 · A1 分支策略检查

**接入位置**：所有调用 `git commit` / `git push` 的入口（包括手动 + AI 内调用）。

**实现**：在 principles §14 中规定 AI 行为，无需改 hook。

```
AI 准备执行 git commit / git push
   ↓
Read .claude/branch-strategy.md
   ↓
不存在？→ 跳过检查（向下兼容 v1.0.22）
存在？→ 提取命名规范段
   ↓
git rev-parse --abbrev-ref HEAD 取当前分支
   ↓
匹配规范？
├─ 是 → 静默执行 commit/push
└─ 否 → 软提醒（不阻塞）：
        "⚠️ 当前分支 `xxx` 不符合 .claude/branch-strategy.md 的命名规范。
         继续 commit / push？(yes/rename)
         rename → 提示 git branch -m <新名>"
```

### 3.4 流程层 · A2 任务认领

**接入位置**：`/harness-req` 创建新版本目录前。

```
用户调 /harness-req <需求>
   ↓
AI 判定路径 + 生成版本号 v0.X-slug
   ↓
Read .claude/assignments/*.md（所有人）
   ↓
检查 v0.X 或 slug 是否被 claim？
├─ 是 → 提醒：
│       "⚠️ alice 已 claim v0.X-slug。
│        [1] 加入协作（多 owner）
│        [2] 改为新版本号
│        [3] 取消"
└─ 否 → 静默执行
   ↓
执行后追加到 .claude/assignments/<我>.md "进行中" 段
```

**多 owner 处理**（D5 决策）：
- 用户选 [1] 加入协作 → 也在自己的 assignments 加 claim 记录
- AI 后续操作时检测多 owner，提醒"X 也在改这个"

## 4. 异常处理

| 场景 | 处理 |
|-----|------|
| `.claude/branch-strategy.md` 不存在 | 跳过分支检查（向下兼容） |
| `.claude/assignments/` 目录不存在 | 跳过冲突预警（向下兼容） |
| assignments/ 目录存在但为空 | 视为无人 claim |
| 多人同时 claim 同任务 | 多 owner 模式（D5）+ 双方都提醒 |
| 用户 claim 后取消任务 | 用户手动改 assignments（移到 done）|
| branch-strategy.md 格式异常 | 警告但不阻塞（fallback 到无 strategy） |
| 协同视角段内容空（AI 无具体提醒） | 强约束：必须 ≥ 2 条 / 视角，否则 AI 必须找出来 |
