## 1. 业务诉求（用户原话）

来自当前会话上下文：
- stock_make_money 已装 v1.0.4
- 我手动覆盖同步了 v1.0.5 / v1.0.7 / v1.0.8 的内容
- CLAUDE.md 头部仍写"v1.0.4 生成"
- 没有官方升级通道——用户不知道怎么从 1.0.4 升到 1.0.8

→ **需求**：提供 `upgrade.sh`，让用户一条命令把已装项目升级到最新 Harness-Lite。

## 2. 用一句话重述

把已装在某项目的 Harness-Lite，干净、安全、不破坏用户数据地升级到最新版本。

---

## 3. 验收标准（AC）

| # | 场景 | 验收 |
|---|------|-----|
| AC1 | 已装 v1.0.4 的项目跑 upgrade | 升到 v1.0.8（settings.json `_version` = 1.0.8、CLAUDE.md 头部 v1.0.4 → v1.0.8） |
| AC2 | 用户的 `team-knowledge/` 不动 | 内容字节级一致 |
| AC3 | 用户的 `docs/versions/active/` 不动 | 内容字节级一致 |
| AC4 | 用户的 `CLAUDE.md` 业务部分不动 | 仅头部版本号字段更新；`{{...}}` 不会再次渲染（可能曾被用户改过） |
| AC5 | 升级前自动备份 | `.harness-lite-upgrade-backup/{ts}/` 含旧 .claude/ + CLAUDE.md |
| AC6 | 升级后跑 validate.sh 全绿 | 5 不变式通过 + skill/agent schema 通过 |
| AC7 | 异常场景：未装 Harness-Lite 的项目 | 拒绝执行（"未检测到 Harness-Lite，请先 init"） |
| AC8 | 异常场景：当前已是最新版 | 提示"已是最新版"并退出 0 |
| AC9 | 用户已自定义的 hook 脚本 | 保留（不覆盖用户改）—— **本版不做**，简单粗暴覆盖（v1.1+ 通过 manifest 解决） |

---

## 4. 不做的范围（明确）

- ❌ **manifest.json** —— 不引入跟踪机制（v1.0.8 根因里已说明：是大工程，留给 v1.1）
- ❌ **多版本回退** —— 不支持 1.0.8 → 1.0.7 降级
- ❌ **跨主版本升级** —— 1.0.x → 1.1.x 时再说（届时可能涉及破坏性变更，需要单独迁移指南）
- ❌ **保留用户改过的 hook 脚本** —— 用户如果改了，会被覆盖（备份里仍能找回）。本版不解决，提示用户做 diff
- ❌ **更新 settings.json 时保留用户加的自定义规则** —— 直接覆盖（用户用 backup 找回）
- ❌ **保留 templates 模板的用户改动** —— 同上

→ **本版定位**：让"装上→新功能→新 skill→bug 修复"的工具流程能走通。复杂合并交给 v1.1+。
